\begin{spacing}{1.0}
\begin{center}
    \textbf{ABSTRAK}\\[0.5cm]
\end{center}

\noindent Penelitian ini merancang dan membangun aplikasi \textit{Point of Sale} (POS) berbasis \textit{mobile} dengan arsitektur \textit{offline-first} yang dilengkapi fitur prediksi penjualan harian menggunakan metode \textit{Long Short-Term Memory} (LSTM), dengan studi kasus kantin EatsTEDI Universitas Gadjah Mada. Sistem dikembangkan menggunakan \textit{framework} Flutter yang terintegrasi dengan basis data lokal Isar DB dan basis data \textit{cloud} Supabase PostgreSQL, sedangkan modul prediksi dibangun menggunakan Python (TensorFlow dan Flask) dan di-\textit{deploy} sebagai layanan API terpisah. Data penelitian berupa 313 hari aktif transaksi yang dimodelkan sebagai deret waktu univariat dengan target \textit{log-return}. Kinerja model diukur menggunakan metrik MAE, RMSE, sMAPE, dan MASE melalui empat skenario pengujian. Pada skema satu langkah ke depan, LSTM \textit{Hybrid} (MAE Rp667.718,00; MASE 1,840) belum mengungguli \textit{baseline Naive} yang mencatat galat terkecil (MAE Rp519.841,00; MASE 1,432), maupun SARIMA dan \textit{Mean-7}, sedangkan \textit{Seasonal-Naive} ($k=4$) memperoleh MASE 2,137. Pengujian \textit{multi-seed} memperlihatkan sebaran MAE yang lebar, yaitu Rp495.527,00 sampai Rp1.048.967,00, sehingga model belum stabil pada ukuran data tersebut. Augmentasi data sintetis TimeGAN menurunkan MAE model multi-langkah sebesar 50,8\%, yaitu dari Rp1.750.355,00 menjadi Rp860.695,00, namun tetap belum melampaui \textit{baseline Seasonal-Naive} pada seluruh horizon $h=1$ sampai $h=7$ hari aktif. Temuan ini menunjukkan bahwa keterbatasan performa bersumber dari volume data, bukan dari arsitektur model, sehingga layanan API produksi menyajikan metode statistik sederhana melalui arsitektur yang bersifat \textit{model-agnostic}. Pengujian \textit{black box} terhadap 12 kasus penggunaan, pengujian \textit{white box} terhadap tiga fungsi kritis layanan prediksi, serta pengujian mekanisme sinkronisasi berhasil seluruhnya, sehingga sistem POS \textit{offline-first} ini layak dioperasikan untuk mendukung operasional UMKM.\\[0.6cm]

\noindent \textbf{Kata Kunci}: \textit{Point of Sale} (POS), Prediksi Penjualan Harian, \textit{Long Short-Term Memory} (LSTM), \textit{Offline-First}, TimeGAN, UMKM
\end{spacing}

\begin{spacing}{1.0}
\begin{center}
    \textbf{\textit{ABSTRACT}}\\[0.5cm]
\end{center}

\noindent \textit{This study designs and develops a mobile-based Point of Sale (POS) application with an offline-first architecture, equipped with a daily sales prediction feature using the Long Short-Term Memory (LSTM) method, with the EatsTEDI canteen of Universitas Gadjah Mada as the case study. The system was developed using the Flutter framework integrated with the local Isar DB database and the Supabase PostgreSQL cloud database, while the prediction module was built using Python (TensorFlow and Flask) and deployed as a separate API service. The research data comprise 313 active transaction days modelled as a univariate time series with a log-return target. Model performance was measured using the MAE, RMSE, sMAPE, and MASE metrics across four testing scenarios. Under the one-step-ahead scheme, the Hybrid LSTM (MAE IDR 667,718.00; MASE 1.840) did not outperform the Naive baseline, which recorded the lowest error (MAE IDR 519,841.00; MASE 1.432), nor SARIMA and Mean-7, while Seasonal-Naive ($k=4$) obtained a MASE of 2.137. Multi-seed testing revealed a wide MAE spread, ranging from IDR 495,527.00 to IDR 1,048,967.00, indicating that the model is not yet stable at this data size. Synthetic data augmentation using TimeGAN reduced the multi-step model MAE by 50.8\%, from IDR 1,750,355.00 to IDR 860,695.00, yet still did not surpass the Seasonal-Naive baseline across all horizons from $h=1$ to $h=7$ active days. These findings indicate that the performance limitation stems from data volume rather than model architecture, hence the production API service presents a simple statistical method through a model-agnostic architecture. Black box testing on 12 use cases, white box testing on three critical prediction-service functions, and synchronisation mechanism testing all succeeded, demonstrating that this offline-first POS system is viable for supporting MSME operations.}\\[0.6cm]

\noindent \textbf{\textit{Keywords}}: \textit{Point of Sale (POS), Daily Sales Prediction, Long Short-Term Memory (LSTM), Offline-First, TimeGAN, MSMEs}

\section{Latar Belakang Masalah}
Transformasi digital pada sektor ritel dan UMKM menjadikan aplikasi \textit{Point of Sale} (POS) sebagai infrastruktur transaksi yang tidak lagi opsional. Selain mencatat penjualan, POS modern menghasilkan data transaksional harian berbentuk deret waktu (\textit{time series}) secara terus-menerus. Namun pada usaha berskala kecil seperti kantin institusi, data tersebut umumnya diposisikan sebatas arsip pelaporan dan belum dimanfaatkan sebagai basis pengambilan keputusan prediktif. Akibatnya penentuan volume produksi harian, pengadaan bahan baku, dan penjadwalan tenaga kerja masih bertumpu pada intuisi pengelola, sehingga berisiko menimbulkan \textit{overstock} maupun \textit{stockout}. Padahal peramalan penjualan yang akurat berperan penting dalam menyeimbangkan permintaan dan pasokan serta meningkatkan profitabilitas ritel~[1].

Data penjualan harian usaha kuliner institusional memiliki karakteristik yang kompleks, yaitu musiman mingguan (hari kerja versus akhir pekan), pengaruh kalender akademik, hari libur nasional, serta fluktuasi tidak beraturan. Metode statistik konvensional seperti \textit{moving average} dan ARIMA terbatas dalam menangkap pola non-linear dan ketergantungan temporal jangka panjang semacam itu. Sebagai alternatif, \textit{Long Short-Term Memory} (LSTM) memanfaatkan mekanisme gerbang untuk mempertahankan informasi lintas rentang waktu panjang sekaligus mengatasi \textit{vanishing gradient} pada RNN tradisional~[2]. Keunggulannya ditunjukkan oleh sejumlah penelitian terkini: optimasi \textit{hyperparameter} LSTM dengan Keras Tuner pada \textit{dataset} ritel Walmart meningkatkan akurasi secara signifikan dibanding metode tradisional~[3]; De Castro Moraes dkk.~[4] mengembangkan arsitektur hibrida CNN-LSTM bertumpuk dan paralel untuk 500 deret waktu ritel; dan Mansur dkk.~[1] mencapai MAPE 4,16\% dengan CNN-LSTM yang diperkaya variabel eksogen, mengungguli ANN, CNN, dan LSTM tunggal.

Kendati demikian, hasil-hasil tersebut sulit direplikasi pada usaha berskala kecil karena dua kondisi. Pertama, model \textit{deep learning} bersifat \textit{data-hungry} sehingga pelatihan dengan data tidak memadai membatasi kegunaannya~[5]; akurasi tinggi pada~[4] dicapai dengan riwayat transaksi lima tahun. Kedua, ketika akurasi tinggi tercapai pada data kecil, keberhasilan itu bertumpu pada kekayaan variabel eksogen, bukan panjang deret waktu. Penelitian~[1] hanya menggunakan enam bulan data satu gerai, namun dengan tambahan tujuh variabel cuaca dan peristiwa, dan penulisnya sendiri mencatat indikasi \textit{overfitting} pada kurva \textit{validation loss}. Untuk kasus tanpa variabel eksogen semacam itu, augmentasi data sintetis dengan \textit{Time-series Generative Adversarial Network} (TimeGAN)~[6] diusulkan dan terbukti menurunkan RMSE serta MAE pada beberapa domain~[7]. Namun manfaat augmentasi dilaporkan menyusut seiring bertambahnya ukuran data awal~[8], sehingga efektivitasnya pada data penjualan harian berskala kecil masih merupakan pertanyaan terbuka.

Dua celah lain bersifat metodologis dan implementatif. Secara metodologis, penelitian peramalan berbasis LSTM umumnya membandingkan modelnya dengan sesama model \textit{machine learning} dan jarang mengujinya terhadap \textit{baseline} heuristik seperti \textit{seasonal-naive}, padahal pada data dengan musiman mingguan kuat \textit{baseline} semacam ini kerap sangat kompetitif dan wajib disertakan sebagai kontrol metodologis~[9]. Secara implementatif, kajian yang ada umumnya berhenti pada tahap eksperimen model dan belum menyatukannya ke dalam aplikasi POS yang benar-benar digunakan pengguna akhir, sehingga jarak antara riset akademik dan penerapan praktis masih lebar~[10].

Studi kasus penelitian ini menggunakan data transaksi platform EatsTEDI pada Departemen Teknik Elektro dan Informatika (DTEDI), Universitas Gadjah Mada, dengan rentang efektif 26 Agustus 2024 sampai 20 Juni 2026 (lebih kurang 22 bulan, 313 hari dengan transaksi tercatat dari 475 hari kerja kalender). Hari tanpa transaksi bukan kehilangan data acak, melainkan cerminan langsung ritme institusional yang justru menjadi objek pemodelan. Rentang tersebut mencakup empat semester berturut-turut atau dua tahun akademik penuh, sehingga pola perkuliahan normal, minggu UTS, minggu UAS, dan libur antarsemester teramati berulang dan berpeluang dipelajari sebagai pola, bukan anomali. Namun dengan hanya 313 titik pengamatan, sampel pelatihan tetap sangat terbatas dibanding penelitian sejenis yang memakai ribuan hingga jutaan catatan~[3], [4]. Kombinasi ini menjadikan EatsTEDI lingkungan uji yang tepat: cukup kaya secara pola musiman untuk menjadi persoalan peramalan yang bermakna, namun cukup terbatas secara volume untuk menguji secara jujur apakah kompleksitas LSTM dan augmentasi TimeGAN benar-benar memberi nilai tambah dibanding pendekatan sederhana.

Berdasarkan uraian tersebut, penelitian ini merancang dan membangun aplikasi \textit{Point of Sale} dengan fitur prediksi penjualan harian menggunakan LSTM, dengan tiga kontribusi. Pertama, perancangan arsitektur POS yang mengintegrasikan modul prediksi ke dalam alur kerja transaksi harian sehingga hasil peramalan langsung dapat dimanfaatkan pengelola. Kedua, evaluasi empiris pengaruh augmentasi TimeGAN terhadap performa LSTM pada \textit{dataset} penjualan berskala kecil. Ketiga, pembandingan model terhadap \textit{baseline seasonal-naive} pada beberapa horizon peramalan sebagai kontrol metodologis, guna menghasilkan rekomendasi yang jujur mengenai kondisi di mana \textit{deep learning} layak diterapkan pada usaha kuliner berskala kecil di Indonesia.

\section{Rumusan Masalah}
Berdasarkan latar belakang yang telah diuraikan, rumusan masalah dalam penelitian ini adalah sebagai berikut:
\begin{enumerate}
    \item Bagaimana merancang dan membangun aplikasi \textit{Point of Sale} yang mengintegrasikan fitur prediksi penjualan harian ke dalam alur kerja transaksi, sehingga hasil peramalan dapat langsung dimanfaatkan oleh pengelola usaha?
    \item Bagaimana menerapkan model \textit{Long Short-Term Memory} untuk memprediksi penjualan harian pada \textit{dataset} EatsTEDI yang berjumlah 313 titik pengamatan, serta bagaimana pengaruh augmentasi data sintetis \textit{Time-series Generative Adversarial Network} (TimeGAN) terhadap akurasi model tersebut?
    \item Bagaimana tingkat akurasi model \textit{Long Short-Term Memory} dibandingkan terhadap \textit{baseline seasonal-naive} pada beberapa horizon peramalan?
\end{enumerate}

\section{Tujuan Penelitian}
Sejalan dengan rumusan masalah tersebut, penelitian ini bertujuan untuk:
\begin{enumerate}
    \item Merancang dan membangun aplikasi \textit{Point of Sale} berbasis \textit{mobile} yang mengintegrasikan fitur prediksi penjualan harian ke dalam alur kerja transaksi, serta menguji fungsionalitasnya melalui pengujian sistem.
    \item Menerapkan model \textit{Long Short-Term Memory} untuk prediksi penjualan harian pada \textit{dataset} EatsTEDI dan menganalisis pengaruh augmentasi data sintetis TimeGAN terhadap akurasi model pada kondisi data pelatihan yang terbatas.
    \item Mengukur tingkat akurasi model \textit{Long Short-Term Memory} terhadap \textit{baseline seasonal-naive} pada beberapa horizon peramalan, guna menghasilkan rekomendasi mengenai kondisi kelayakan penerapan pendekatan \textit{deep learning} pada usaha kuliner berskala kecil.
\end{enumerate}

\section{Batasan Masalah}
Agar penelitian ini terarah dan terukur, ditetapkan batasan sebagai berikut:
\begin{enumerate}
    \item Sumber dan cakupan data. Data yang digunakan adalah data transaksi platform EatsTEDI pada Departemen Teknik Elektro dan Informatika (DTEDI), Universitas Gadjah Mada, dengan rentang efektif 26 Agustus 2024 sampai dengan 20 Juni 2026 dan menghasilkan 313 hari dengan transaksi tercatat. Pemodelan dilakukan secara \textit{univariat} dengan variabel target berupa total nilai penjualan harian, tanpa menyertakan variabel eksogen seperti kondisi cuaca, promosi, maupun harga karena tidak tersedia pada \textit{dataset}.
    \item Granularitas prediksi. Prediksi dilakukan pada tingkat agregat penjualan harian, bukan pada tingkat \textit{item} atau kategori produk secara individual.
    \item Cakupan metode. Metode peramalan yang dikembangkan dibatasi pada arsitektur \textit{Long Short-Term Memory} dengan augmentasi data sintetis TimeGAN, serta dibandingkan terhadap model pembanding berupa \textit{Naive}, \textit{Mean-7}, \textit{Seasonal-Naive}, dan SARIMA. Arsitektur \textit{deep learning} lain seperti \textit{Transformer} dan \textit{Temporal Fusion Transformer}, maupun metode augmentasi lain seperti \textit{jittering} dan \textit{window warping}, tidak menjadi objek pengujian dalam penelitian ini.
    \item Metrik evaluasi. Evaluasi performa model menggunakan metrik MAE, RMSE, sMAPE, dan MASE. Metrik MAPE konvensional tidak digunakan karena rentan menghasilkan galat persentase yang tidak representatif pada hari dengan nilai pendapatan sangat rendah.
    \item Cakupan aplikasi dan pengujian. Aplikasi POS dikembangkan pada platform Android menggunakan \textit{framework} Flutter, dengan model dilatih secara luring (\textit{offline}) dan hasil pelatihannya diintegrasikan sebagai layanan prediksi. Pengembangan untuk platform iOS serta mekanisme pelatihan ulang otomatis (\textit{online} atau \textit{incremental learning}) berada di luar cakupan penelitian. Pengujian dibatasi pada pengujian fungsional dan struktural sistem serta pengujian akurasi model, tanpa mencakup pengukuran dampak ekonomi penerapan sistem.
\end{enumerate}

\section{Manfaat Penelitian}
Manfaat dari penelitian ini diharapkan mampu menyediakan sebuah aplikasi \textit{Point of Sale} yang tidak hanya mencatat transaksi, tetapi juga menyajikan estimasi penjualan harian sebagai bahan pertimbangan pengelola dalam menentukan volume produksi, pengadaan bahan baku, dan penjadwalan tenaga kerja. Secara keilmuan, penelitian ini memberikan bukti empiris mengenai performa \textit{Long Short-Term Memory} beserta augmentasi TimeGAN pada data penjualan harian berskala kecil, suatu kondisi yang selama ini kurang terwakili dalam literatur peramalan ritel. Penyertaan \textit{baseline seasonal-naive} sebagai kontrol metodologis menjadikan hasil perbandingan tersebut dapat dipakai sebagai rekomendasi berbasis bukti bagi pelaku usaha mikro, kecil, dan menengah mengenai kondisi kelayakan penerapan \textit{deep learning}, sekaligus sebagai rujukan teknis bagi pengembang perangkat lunak dalam menyatukan model peramalan ke dalam aplikasi \textit{mobile}.

\section{\textit{State of the Art}}

Kajian \textit{state of the art} pada subbab ini disusun untuk memetakan posisi penelitian yang dilakukan terhadap penelitian-penelitian terdahulu yang relevan. Penelusuran literatur difokuskan pada empat kelompok kajian yang saling berkaitan.

Kelompok pertama adalah penelitian yang menerapkan \textit{Long Short-Term Memory} dan variannya untuk peramalan penjualan ritel. Kelompok kajian ini menunjukkan kecenderungan yang konsisten, yaitu bahwa arsitektur berbasis LSTM mampu menangkap ketergantungan temporal dan pola musiman pada data penjualan secara lebih baik dibandingkan metode statistik konvensional. Namun demikian, sebagian besar penelitian pada kelompok ini menggunakan \textit{dataset} berskala besar dengan rentang pengamatan bertahun-tahun, sehingga hasilnya belum tentu dapat direplikasi pada skala usaha kecil.

Kelompok kedua adalah penelitian yang mengkaji augmentasi data sintetis, khususnya menggunakan \textit{Time-series Generative Adversarial Network} (TimeGAN), sebagai upaya mengatasi keterbatasan jumlah sampel pelatihan. Kelompok ini memperlihatkan hasil yang belum sepenuhnya konvergen: sebagian penelitian melaporkan penurunan galat yang signifikan, sementara sebagian lain mencatat bahwa manfaat augmentasi menurun seiring bertambahnya ukuran data awal.

Kelompok ketiga adalah penelitian yang menyoroti pentingnya \textit{baseline} sederhana sebagai kontrol metodologis dalam evaluasi model peramalan. Kelompok ini menjadi penting karena beberapa penelitian menunjukkan bahwa metode sederhana masih dapat mengungguli model \textit{deep learning} pada kondisi data tertentu.

Kelompok keempat adalah penelitian yang mengintegrasikan modul peramalan ke dalam aplikasi \textit{Point of Sale}. Kelompok ini masih relatif terbatas jumlahnya, dan sebagian besar penelitian di Indonesia pada kelompok ini menggunakan metode statistik atau \textit{machine learning} konvensional, bukan \textit{deep learning}.

Berdasarkan pemetaan pada Tabel~\ref{tab:sota}, dapat diidentifikasi bahwa belum terdapat penelitian yang secara bersamaan melakukan tiga hal berikut: menerapkan LSTM untuk prediksi penjualan harian pada \textit{dataset} berskala kecil dengan karakteristik deret tidak sinambung, menguji kontribusi augmentasi sintetis TimeGAN pada kondisi tersebut, serta mengintegrasikan model hasil pelatihan ke dalam aplikasi \textit{Point of Sale} yang benar-benar digunakan pengguna akhir dan mengevaluasinya terhadap \textit{baseline seasonal-naive}. Ketiga aspek inilah yang menjadi kebaruan penelitian ini.

\section{Tinjauan Teoritis}

\subsection{\textit{Point of Sale} (POS)}

\textit{Point of Sale} (POS) adalah sistem yang digunakan untuk mencatat, memproses, dan mendokumentasikan transaksi penjualan pada titik terjadinya transaksi. Dalam perkembangannya, aplikasi POS tidak lagi berfungsi semata sebagai mesin kasir digital, melainkan juga sebagai sistem informasi yang mengelola data produk, persediaan, pelanggan, dan pelaporan keuangan. Penerapan aplikasi POS pada usaha mikro, kecil, dan menengah terbukti membantu proses pencatatan transaksi menjadi lebih cepat, akurat, dan terdokumentasi, meskipun tingkat penerimaan penggunanya masih dipengaruhi oleh persepsi kemudahan dan kemanfaatan sistem [14]. Secara arsitektural, sistem POS umumnya terdiri atas modul autentikasi pengguna, modul manajemen produk, modul transaksi, modul persediaan, dan modul pelaporan [15].

Data transaksi yang dihasilkan aplikasi POS secara berkelanjutan memiliki sifat deret waktu, yakni terurut berdasarkan waktu dan memiliki ketergantungan antarpengamatan [16]. Sifat inilah yang membuka peluang pemanfaatan data POS untuk keperluan peramalan, sehingga sistem tidak hanya bersifat \textit{descriptive} (mencatat apa yang telah terjadi) tetapi juga \textit{predictive} (memperkirakan apa yang akan terjadi), sebagaimana telah diterapkan pada sistem POS ritel yang menyertakan modul prediksi penjualan [10], [13].

\subsection{Peramalan Deret Waktu (\textit{Time Series Forecasting})}

Deret waktu adalah rangkaian pengamatan suatu variabel yang dicatat secara berurutan dalam interval waktu yang tetap. Peramalan deret waktu bertujuan memperkirakan nilai pengamatan pada periode mendatang berdasarkan pola yang terkandung pada pengamatan historisnya [16]. Secara umum, sebuah deret waktu dapat diuraikan menjadi empat komponen, yaitu tren (\textit{trend}), musiman (\textit{seasonality}), siklus (\textit{cyclical}), dan komponen tak beraturan (\textit{irregular} atau \textit{noise}) [16], [17].

Suatu deret waktu dapat memuat lebih dari satu periode musiman sekaligus, sehingga pemodelannya perlu memperhitungkan setiap periode yang relevan [16]. Pada data penjualan harian kantin institusional, komponen musiman muncul dalam dua tingkatan. Musiman mingguan (periode $m = 7$) tampak dari perbedaan volume transaksi antara hari kerja dan akhir pekan, sedangkan musiman berbasis kalender akademik muncul dari perbedaan antara masa perkuliahan, minggu ujian, dan masa libur antarsemester. Pola musiman berbasis kalender semacam ini juga dilaporkan berpengaruh nyata terhadap volume penjualan ritel harian [1].

Pendekatan peramalan secara garis besar terbagi menjadi tiga kelompok. \textit{Pertama}, pendekatan statistik klasik seperti \textit{moving average}, \textit{exponential smoothing}, ARIMA, dan SARIMA, yang mengasumsikan hubungan linear antarpengamatan [17]. \textit{Kedua}, pendekatan \textit{machine learning} seperti \textit{Random Forest}, \textit{Support Vector Regression}, dan \textit{Gradient Boosting}, yang memperlakukan peramalan sebagai persoalan regresi dengan fitur temporal yang direkayasa secara manual [13]. \textit{Ketiga}, pendekatan \textit{deep learning} seperti RNN, LSTM, dan GRU, yang mampu mempelajari representasi temporal secara otomatis tanpa rekayasa fitur eksplisit [2], [4]. Perbandingan lintas ketiga kelompok pendekatan tersebut pada kompetisi peramalan berskala besar menunjukkan bahwa tidak ada satu kelompok yang unggul secara mutlak, sehingga pemilihannya bergantung pada karakteristik dan ukuran data yang tersedia [9].

\subsection{\textit{Baseline Seasonal-Naive}}

\textit{Seasonal-naive} adalah metode peramalan paling sederhana untuk data bermusiman, yang memperkirakan nilai suatu periode sama dengan nilai pada periode musiman terakhir yang bersesuaian [16]. Secara matematis, prediksi untuk waktu $t+h$ dirumuskan sebagai:
\begin{equation}
    \hat{y}_{t+h} = y_{t+h-m\lfloor (h-1)/m \rfloor - m}
\end{equation}

\noindent dengan $m$ adalah panjang periode musiman. Untuk data penjualan harian dengan musiman mingguan, $m = 7$, sehingga prediksi hari Senin depan adalah nilai penjualan hari Senin sebelumnya.

Meskipun sederhana, metode ini memiliki peran metodologis yang penting. Hyndman dan Koehler menegaskan bahwa metode naif berfungsi sebagai penyebut normalisasi dalam pengukuran akurasi peramalan, sehingga akurasi suatu model hanya bermakna apabila dinyatakan secara relatif terhadap metode naif tersebut [18]. Pengalaman kompetisi peramalan berskala besar juga menunjukkan bahwa metode sederhana kerap sulit dikalahkan oleh model kompleks, terutama pada deret waktu yang pendek atau sangat bergejolak [9]. Karena itu, penyertaan \textit{baseline seasonal-naive} dalam penelitian ini berfungsi sebagai kontrol metodologis untuk memastikan bahwa keunggulan model LSTM, apabila ada, benar-benar berasal dari kemampuan pemodelan dan bukan sekadar dari pola musiman yang telah dapat ditangkap oleh heuristik sederhana.

\subsection{\textit{Recurrent Neural Network} (RNN)}

\textit{Recurrent Neural Network} adalah arsitektur jaringan saraf tiruan yang dirancang untuk memproses data sekuensial dengan cara mempertahankan keadaan tersembunyi (\textit{hidden state}) yang diperbarui pada setiap langkah waktu [2]. Pada langkah waktu $t$, keadaan tersembunyi dihitung sebagai [2]:
\begin{equation}
    h_t = \tanh(W_{xh} x_t + W_{hh} h_{t-1} + b_h)
\end{equation}

\noindent dengan $x_t$ sebagai masukan pada waktu $t$, $h_{t-1}$ sebagai keadaan tersembunyi sebelumnya, serta $W$ dan $b$ sebagai bobot dan bias yang dipelajari.

Kelemahan utama RNN konvensional adalah masalah \textit{vanishing gradient}, yaitu mengecilnya nilai gradien secara eksponensial ketika dipropagasikan mundur melintasi banyak langkah waktu. Akibatnya, RNN kesulitan mempelajari ketergantungan jangka panjang [2].

\subsection{\textit{Long Short-Term Memory} (LSTM)}

\textit{Long Short-Term Memory} diperkenalkan oleh Hochreiter dan Schmidhuber sebagai pengembangan RNN yang mengatasi masalah \textit{vanishing gradient} melalui penambahan sel memori (\textit{cell state}) dan tiga mekanisme gerbang (\textit{gating mechanism}) [2]. Sel memori berfungsi sebagai jalur informasi yang memungkinkan gradien mengalir tanpa mengalami peluruhan berlebih, sedangkan gerbang mengendalikan informasi mana yang dibuang, disimpan, dan dikeluarkan.

\noindent\textbf{a. Gerbang Lupa (\textit{Forget Gate})}

Gerbang lupa menentukan proporsi informasi dari sel memori sebelumnya yang akan dipertahankan [2]:
\begin{equation}
    f_t = \sigma(W_f \cdot [h_{t-1}, x_t] + b_f)
    \label{eq:gerbang-lupa}
\end{equation}

\noindent dengan $\sigma$ adalah fungsi aktivasi sigmoid yang menghasilkan nilai pada rentang $[0, 1]$. Nilai mendekati 0 berarti informasi dibuang, sedangkan nilai mendekati 1 berarti informasi dipertahankan.

\noindent\textbf{b. Gerbang Masukan (\textit{Input Gate})}

Gerbang masukan menentukan informasi baru yang akan disimpan ke dalam sel memori. Tahap ini terdiri atas dua bagian, yaitu penentuan proporsi pembaruan dan pembentukan kandidat nilai baru [2]:
\begin{equation}
    i_t = \sigma(W_i \cdot [h_{t-1}, x_t] + b_i)
    \label{eq:gerbang-masukan}
\end{equation}
\begin{equation}
    \tilde{C}_t = \tanh(W_C \cdot [h_{t-1}, x_t] + b_C)
    \label{eq:kandidat-sel}
\end{equation}

\noindent\textbf{c. Pembaruan Sel Memori (\textit{Cell State Update})}

Sel memori diperbarui dengan menggabungkan informasi lama yang dipertahankan dan informasi baru yang diterima [2]:
\begin{equation}
    C_t = f_t \odot C_{t-1} + i_t \odot \tilde{C}_t
    \label{eq:pembaruan-sel}
\end{equation}

\noindent dengan $\odot$ menyatakan perkalian elemen per elemen (\textit{Hadamard product}).

\noindent\textbf{d. Gerbang Keluaran (\textit{Output Gate})}

Gerbang keluaran menentukan bagian sel memori yang akan diteruskan sebagai keadaan tersembunyi [2]:
\begin{equation}
    o_t = \sigma(W_o \cdot [h_{t-1}, x_t] + b_o)
    \label{eq:gerbang-keluaran}
\end{equation}
\begin{equation}
    h_t = o_t \odot \tanh(C_t)
    \label{eq:keadaan-tersembunyi}
\end{equation}

Melalui mekanisme tersebut, LSTM mampu mempelajari pola berulang berjangka panjang seperti musiman mingguan pada data penjualan. Sejumlah penelitian membuktikan efektivitasnya pada peramalan penjualan ritel, baik dalam bentuk LSTM tunggal dengan optimasi \textit{hyperparameter} [3] maupun dalam bentuk arsitektur hibrida dengan CNN [1], [4].

\subsection{\textit{Generative Adversarial Network} (GAN) dan TimeGAN}

\textit{Generative Adversarial Network} (GAN) adalah kerangka pemodelan generatif yang melatih dua jaringan secara bersamaan dalam skema permainan minimaks, yaitu \textit{generator} $G$ yang menghasilkan data sintetis dan \textit{discriminator} $D$ yang membedakan data asli dari data sintetis [19]. Fungsi objektifnya dirumuskan sebagai:
\begin{equation}
    \min_G \max_D V(D,G) = \mathbb{E}_{x \sim p_{data}(x)}[\log D(x)] + \mathbb{E}_{z \sim p_z(z)}[\log(1 - D(G(z)))]
\end{equation}

GAN konvensional dirancang untuk data yang tidak memiliki urutan, sehingga kurang mampu mempertahankan dinamika temporal ketika diterapkan pada deret waktu. Untuk mengatasi hal tersebut, Yoon dkk. mengusulkan \textit{Time-series Generative Adversarial Network} (TimeGAN), yang memadukan kerangka \textit{adversarial} dengan pembelajaran swa-penyeliaan (\textit{self-supervised learning}) berbasis \textit{autoencoder} [6]. Arsitektur TimeGAN terdiri atas empat komponen [6]:
\begin{enumerate}
    \item \textbf{\textit{Embedding function}}, memetakan data asli dari ruang fitur ke ruang laten.
    \item \textbf{\textit{Recovery function}}, merekonstruksi data dari ruang laten kembali ke ruang fitur.
    \item \textbf{\textit{Generator}}, menghasilkan barisan laten sintetis dari vektor derau acak.
    \item \textbf{\textit{Discriminator}}, membedakan barisan laten asli dari barisan laten sintetis.
\end{enumerate}

Keempat komponen dilatih menggunakan kombinasi tiga fungsi galat, yaitu \textit{reconstruction loss}, \textit{unsupervised adversarial loss}, dan \textit{supervised loss} [6]. Komponen \textit{supervised loss} inilah yang secara khusus memaksa \textit{generator} mempelajari transisi antarlangkah waktu, sehingga dinamika temporal data asli dapat dipertahankan pada data sintetis yang dihasilkan.

Dalam konteks penelitian ini, TimeGAN digunakan sebagai metode augmentasi data untuk memperbanyak sampel pelatihan pada \textit{dataset} yang berjumlah terbatas. Penerapan serupa telah dilaporkan berhasil menurunkan RMSE dan MAE pada domain konsumsi energi [7]. Namun demikian, perlu dicatat bahwa manfaat augmentasi tidak bersifat universal; kajian perbandingan sistematis menunjukkan bahwa keuntungan augmentasi cenderung menurun seiring bertambahnya ukuran data awal maupun berkurangnya kedalaman arsitektur jaringan [8].

\subsection{Praproses Data}

\noindent\textbf{a. Normalisasi}

Normalisasi diperlukan agar seluruh nilai masukan berada pada rentang yang seragam, sehingga mempercepat konvergensi pelatihan dan mencegah dominasi fitur bernilai besar. Metode yang umum digunakan pada LSTM adalah \textit{Min-Max Scaling} [3], [4]:
\begin{equation}
    x' = \frac{x - x_{min}}{x_{max} - x_{min}}
\end{equation}

\noindent\textbf{b. Pembentukan Jendela Geser (\textit{Sliding Window})}

Data deret waktu univariat perlu diubah menjadi format pembelajaran terbimbing melalui teknik \textit{sliding window} [8]. Dengan panjang jendela $w$, setiap sampel pelatihan terdiri atas masukan $[y_{t-w+1}, \dots, y_t]$ dan target $y_{t+1}$. Jumlah sampel yang terbentuk adalah $N - w$, dengan $N$ sebagai jumlah pengamatan. Konsekuensinya, semakin panjang jendela yang digunakan, semakin sedikit sampel pelatihan yang tersedia, yaitu pertimbangan yang menjadi kritis pada \textit{dataset} berukuran terbatas seperti pada penelitian ini.

\noindent\textbf{c. Pembagian Data}

Berbeda dengan data yang tidak berurutan, pembagian data deret waktu tidak boleh dilakukan secara acak karena akan menimbulkan kebocoran informasi masa depan (\textit{data leakage}). Pembagian dilakukan secara kronologis, dengan data terawal sebagai data latih dan data terakhir sebagai data uji [16].

\subsection{Metrik Evaluasi}

Evaluasi akurasi model peramalan dalam penelitian ini menggunakan metrik berikut, yang mengacu pada tinjauan Hyndman dan Koehler mengenai ukuran akurasi peramalan [18], dengan $y_i$ sebagai nilai aktual, $\hat{y}_i$ sebagai nilai prediksi, dan $n$ sebagai jumlah pengamatan.

\noindent\textbf{a. \textit{Mean Absolute Error} (MAE)}
\begin{equation}
    \text{MAE} = \frac{1}{n}\sum_{i=1}^{n} |y_i - \hat{y}_i|
\end{equation}

\noindent\textbf{b. \textit{Root Mean Squared Error} (RMSE)}
\begin{equation}
    \text{RMSE} = \sqrt{\frac{1}{n}\sum_{i=1}^{n} (y_i - \hat{y}_i)^2}
\end{equation}

\noindent\textbf{c. \textit{Mean Absolute Percentage Error} (MAPE)}
\begin{equation}
    \text{MAPE} = \frac{100\%}{n}\sum_{i=1}^{n} \left| \frac{y_i - \hat{y}_i}{y_i} \right|
\end{equation}

MAPE memudahkan interpretasi karena dinyatakan dalam persentase, namun tidak terdefinisi ketika terdapat nilai aktual sama dengan nol dan bersifat asimetris terhadap galat berlebih maupun kurang [18]. Keterbatasan ini relevan bagi penelitian ini mengingat \textit{dataset} memuat hari-hari tanpa transaksi.

\noindent\textbf{d. \textit{symmetric Mean Absolute Percentage Error} (sMAPE)}

Untuk mengatasi keterbatasan MAPE tersebut digunakan varian simetrisnya, yaitu sMAPE, yang membagi galat absolut terhadap rata-rata nilai aktual dan nilai prediksi sehingga tidak meledak ketika nilai aktual mendekati nol dan memiliki batas atas galat sebesar 200\% [18].
\begin{equation}
    \text{sMAPE} = \frac{100\%}{n}\sum_{i=1}^{n} \frac{|y_i - \hat{y}_i|}{(|y_i| + |\hat{y}_i|)/2}
\end{equation}

Sebagai konvensi implementasi, apabila penyebut bernilai nol karena nilai aktual dan nilai prediksi sama-sama nol, penyebut diganti dengan nilai 1 agar tidak terjadi galat pembagian dengan nol (\textit{division by zero}).

\noindent\textbf{e. \textit{Mean Absolute Scaled Error} (MASE)}

Berbeda dengan ketiga metrik sebelumnya yang berdiri sendiri, MASE memungkinkan perbandingan langsung terhadap \textit{baseline} karena galat model dinormalisasi terhadap galat metode naif. Metrik ini diusulkan Hyndman dan Koehler [18] dan dirumuskan sebagai berikut:
\begin{equation}
    \text{MASE} = \frac{\frac{1}{n}\sum_{i=1}^{n} |y_i - \hat{y}_i|}{\frac{1}{N-m}\sum_{t=m+1}^{N} |y_t - y_{t-m}|}
\end{equation}

\noindent dengan penyebut dihitung khusus dari data latih, yaitu $N$ menyatakan jumlah pengamatan pada data latih dan $m$ panjang periode musiman, agar nilai MASE sebanding dengan yang dilaporkan pada literatur. Nilai MASE kurang dari 1 menunjukkan bahwa model berkinerja lebih baik daripada \textit{baseline seasonal-naive}, sedangkan nilai lebih dari 1 menunjukkan sebaliknya. Metrik ini menjadikan perbandingan terhadap \textit{baseline} bersifat eksplisit dan terukur.

\subsection{Flutter}

Flutter adalah \textit{framework} pengembangan aplikasi lintas platform yang dikembangkan Google, menggunakan bahasa pemrograman Dart dan menerapkan pendekatan berbasis \textit{widget} dengan mesin perenderan tersendiri [20]. Pemilihan Flutter dalam penelitian ini didasarkan pada kemampuannya menghasilkan aplikasi dengan basis kode tunggal, performa mendekati aplikasi asli (\textit{native}), serta dukungan ekosistem pustaka yang memadai untuk integrasi dengan layanan basis data dan antarmuka pemrograman aplikasi (API).

\subsection{Pengujian \textit{Black Box}}

Pengujian \textit{black box}, atau disebut juga \textit{behavioral testing}, adalah metode pengujian yang berfokus pada kesesuaian antara masukan dan keluaran sistem berdasarkan spesifikasi fungsional, tanpa memperhatikan struktur kode maupun logika internal program [21]. Pengujian ini diarahkan untuk menemukan kesalahan berupa fungsi yang tidak benar atau tidak tersedia, kesalahan antarmuka, kesalahan akses basis data, serta kesalahan perilaku dan kinerja sistem [21], dengan teknik perancangan kasus uji yang lazim digunakan meliputi \textit{equivalence partitioning} dan \textit{boundary value analysis} [22], [23]. Dalam penelitian ini, pengujian \textit{black box} diterapkan untuk memverifikasi fungsionalitas aplikasi \textit{Point of Sale} yang dibangun, meliputi modul autentikasi pengguna, manajemen produk, transaksi penjualan, pengelolaan persediaan, pelaporan, serta modul prediksi penjualan harian, dengan setiap kasus uji mencantumkan skenario pengujian, masukan, hasil yang diharapkan, hasil yang diperoleh, dan simpulan berupa ``berhasil'' atau ``gagal''. Metode ini dipilih karena tujuan pengujian adalah memastikan seluruh fungsi aplikasi berperilaku sesuai spesifikasi kebutuhan dari sudut pandang pengguna akhir, sehingga penilaian akurasi model prediksi tidak termasuk dalam cakupan pengujian ini melainkan dilakukan secara terpisah menggunakan metrik yang telah diuraikan pada Subbab 2.2.8.

    \item \textbf{Observasi dan Wawancara}

    Observasi dan wawancara dilakukan terhadap pengelola divisi kewirausahaan mahasiswa platform EatsTEDI di DTEDI Universitas Gadjah Mada. Kegiatan ini bertujuan memahami alur operasional kasir, pencatatan menu harian, pengelolaan stok, serta kendala dalam mengantisipasi sisa produk, sehingga kebutuhan fitur prediksi pada aplikasi dapat dirumuskan sesuai kondisi lapangan.

    \item \textbf{Akuisisi Data}

    Data transaksi diperoleh langsung dari pengelola platform EatsTEDI dalam bentuk berkas \textit{dump} SQL. Berkas tersebut memuat tabel \textit{invoices} yang menjadi sumber utama nilai transaksi, beserta tabel pendukung \textit{product\_sold}, \textit{products}, dan \textit{categories}. Data digunakan sebagai data utama penelitian karena merupakan catatan transaksi riil yang berkesinambungan selama dua tahun akademik penuh.

    \item \textbf{Praproses Data}

    Tahap praproses dilakukan untuk menyesuaikan data dengan kebutuhan pemodelan deret waktu, yang meliputi:
    \begin{enumerate}[label=\arabic*)]
        \item Penyaringan transaksi berdasarkan status pelunasan;
        \item Agregasi nilai transaksi menurut tanggal menjadi pendapatan harian;
        \item Normalisasi nilai menggunakan \textit{Min-Max Scaling};
        \item Pembentukan sampel pembelajaran terbimbing melalui teknik \textit{sliding window}.
    \end{enumerate}
    Hasil dari tahap ini adalah \textit{dataset} final berupa deret waktu univariat yang digunakan sebagai masukan dalam proses pelatihan dan evaluasi model.
\end{enumerate}

\section{Perancangan Sistem}

Perancangan sistem merupakan tahap yang bertujuan memberikan gambaran mengenai bagaimana aplikasi \textit{Point of Sale} dengan fitur prediksi penjualan harian akan dibangun dan dioperasikan. Tahap perancangan ini mencakup penyusunan arsitektur sistem, pemodelan menggunakan \textit{Unified Modeling Language} (UML), serta perancangan antarmuka pengguna (\textit{user interface}). Adapun rincian perancangan sistem dalam penelitian ini dijelaskan sebagai berikut.

\subsection{Arsitektur Sistem}

Sistem Parzello POS Mobile dirancang menggunakan pendekatan arsitektur \textit{hybrid-cloud} yang membagi pemrosesan antara perangkat lokal dan infrastruktur \textit{cloud}. Secara keseluruhan, sistem terdiri dari empat komponen utama yang saling terintegrasi, yaitu \textit{Flutter Mobile App}, \textit{Supabase Cloud}, \textit{Firebase}, dan \textit{Layanan Inferensi Model LSTM} (Hugging Face). Rancangan arsitektur sistem diilustrasikan pada Gambar \ref{fig:arsitektur_sistem}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.85\textwidth]{arsitektur_sistem}
    \caption{Arsitektur Sistem POS}
    \label{fig:arsitektur_sistem}
\end{figure}

Penjelasan mengenai empat komponen utama dalam arsitektur sistem adalah sebagai berikut:
\begin{enumerate}
    \item \textbf{Sisi Klien (\textit{Client-Side}):} Aplikasi dibangun menggunakan \textit{framework} Flutter dengan manajemen \textit{state} Riverpod dan navigasi GoRouter. Isar DB berperan sebagai basis data lokal agar kasir tetap dapat bertransaksi meskipun koneksi terputus, sedangkan \textit{sync engine} menyinkronkan data ke \textit{cloud} menggunakan penanda \textit{isSynced} untuk menghindari duplikasi.
    \item \textbf{Infrastruktur \textit{Cloud} (Supabase):} Supabase menjadi tulang punggung infrastruktur \textit{cloud} melalui empat layanan. Supabase Auth menangani autentikasi pengguna, sedangkan Supabase PostgreSQL berperan sebagai basis data relasional terpusat yang dilengkapi kebijakan \textit{Row Level Security} untuk mengisolasi data antartoko serta prosedur tersimpan (\textit{RPC}) untuk memproses transaksi secara aman. Supabase Storage menyimpan aset media, dan \textit{Edge Functions} memproses \textit{webhook} basis data seperti pemicu notifikasi stok menipis.
    \item \textbf{Telemetri dan Notifikasi (Firebase):} Sistem terintegrasi dengan Firebase untuk telemetri dan notifikasi. \textit{Firebase Cloud Messaging} menyampaikan \textit{push notification} kepada staf toko, misalnya peringatan stok menipis, sedangkan \textit{Firebase Analytics} mencatat perilaku penggunaan aplikasi seperti volume transaksi harian dan frekuensi pemakaian fitur prediksi.
    \item \textbf{Layanan Inferensi Model LSTM (Hugging Face):} Model \textit{Long Short-Term Memory} dikemas sebagai layanan \textit{REST API} berbasis Flask yang di-\textit{deploy} pada platform Hugging Face, sehingga dapat diakses tanpa infrastruktur \textit{server} tersendiri. Aplikasi memanggil \textit{endpoint} tersebut melalui HTTPS dengan \textit{payload} berupa data agregat penjualan, lalu menerima hasil prediksi dalam format JSON yang disimpan sebagai \textit{snapshot} pada Supabase.
\end{enumerate}

Gambar~\ref{fig:lstm_alur} menunjukkan proses penerapan metode yang dimulai dari penarikan data transaksi harian pada basis data Supabase sebagai masukan sistem. Adapun tahapan proses tersebut dijelaskan sebagai berikut.

\noindent a.~~Input Data Transaksi Harian: Sistem menarik riwayat transaksi harian mitra EatsTEDI dari basis data \textit{cloud} Supabase sebagai masukan proses pemodelan.

\noindent b.~~\textit{Filtering} Hari Non-Aktif: Sistem menghapus hari Sabtu, Minggu, serta bulan Januari dan Juli agar model dilatih murni pada indeks hari kerja aktif tanpa distorsi \textit{gap} panjang.

\noindent c.~~Transformasi Logaritma: Nominal pendapatan $Y_t$ ditransformasikan ke skala logaritma menggunakan $Y'_t = \log(Y_t + 1)$ untuk menstabilkan variansi.

\noindent d.~~Transformasi Target \textit{Log-Return}: Target prediksi diubah dari nilai pendapatan menjadi perubahan relatif (\textit{log-return}) $r_t$ agar model mewarisi autokorelasi jangka pendek data penjualan, sebagaimana Persamaan~\ref{eq:log-return}.

\begin{equation}
    r_t = Y'_t - Y'_{t-1} = \log(Y_t + 1) - \log(Y_{t-1} + 1)
    \label{eq:log-return}
\end{equation}

\noindent e.~~Pengodean Siklik dan Normalisasi: Fitur waktu diubah menjadi nilai sinus dan kosinus, lalu seluruh fitur dinormalisasi dengan \textit{Min-Max Scaling} ke rentang $[0,1]$. Parameter \textit{scaler} dipasang hanya pada data latih untuk mencegah \textit{data leakage}.

\noindent f.~~Pembentukan \textit{Sequence}: Deret waktu diubah menjadi pasangan urutan melalui \textit{sliding window} sepanjang 7 hari aktif untuk memprediksi 1 hari aktif berikutnya (\textit{one-step-ahead}).

\noindent g.~~Pembagian \textit{Dataset} Kronologis: \textit{Dataset} dibagi secara \textit{time-based split}, yaitu 70\% data latih, 15\% data validasi untuk \textit{early stopping}, dan 15\% data uji.

\noindent h.~~Pembangunan Arsitektur LSTM: Arsitektur dirancang minimalis untuk menghindari \textit{overfitting}, terdiri atas \textit{input layer} $7 \times 8$, satu \textit{LSTM layer} 24 \textit{hidden units}, \textit{dropout} 0,1, \textit{dense layer} 16 neuron ReLU, dan \textit{output layer} satu neuron linear, dengan total 3.585 parameter terlatih.

\noindent i.~~Pelatihan Model: Model dilatih menggunakan optimasi Adam (\textit{learning rate} $5 \times 10^{-4}$), fungsi kerugian MSE, \textit{batch} 16, dan maksimum 200 \textit{epoch}, disertai \textit{Early Stopping} 20 \textit{epoch} dan \textit{Reduce Learning Rate on Plateau} faktor 0,5.

\noindent j.~~Evaluasi Model: Sistem menghitung MAE, RMSE, sMAPE, dan MASE pada data uji sebagaimana dijabarkan pada Subbab~3.4.4.

\noindent k.~~Pemeriksaan Kriteria Kelayakan: Model dinyatakan layak apabila MASE-nya lebih kecil daripada MASE \textit{baseline Naive}. Apabila belum, dilakukan \textit{hyperparameter tuning} dan pelatihan diulang.

\noindent l.~~Rekonstruksi ke Skala Nominal: \textit{Output} berupa \textit{log-return} $\hat{r}_t$ dikembalikan ke skala Rupiah $\hat{Y}_t$ menggunakan nilai penjualan hari sebelumnya, sesuai Persamaan~\ref{eq:rekonstruksi}.

\begin{equation}
    \hat{Y}_{t} = \exp\left(\log(Y_{t-1} + 1) + \hat{r}_{t}\right) - 1
    \label{eq:rekonstruksi}
\end{equation}

\noindent m.~~Prakiraan Rekursif Multi-Langkah: Proyeksi 7 hari aktif ke depan dihasilkan secara rekursif dengan tiga pengaman, yaitu \textit{clipping log-return} pada persentil 10--90, \textit{damping factor} $\varphi^h$ dengan $\varphi = 0{,}7$, dan \textit{safety rail} pada rentang pendapatan historis.

\noindent n.~~Integrasi dan Penyajian Hasil: Model yang layak diintegrasikan ke sistem POS melalui \textit{REST API} berbasis Flask pada Hugging Face, sehingga hasil prediksi dapat ditampilkan pada halaman prediksi penjualan harian.

Proses tersebut diulang hingga model memenuhi kriteria kelayakan. \textit{Flowchart} ini menunjukkan bahwa LSTM diterapkan sebagai model prediksi deret waktu bertarget \textit{log-return}, yang hasilnya direkonstruksi ke skala nominal sebelum disajikan pada aplikasi \textit{Point of Sale}.

Gambar~\ref{fig:sel_lstm} menunjukkan proses pembaruan \textit{cell state} dan \textit{hidden state} yang diulang sebanyak panjang \textit{sequence} masukan, yaitu 7 langkah waktu. Adapun tahapan proses tersebut dijelaskan sebagai berikut.

\noindent a.~~Input Vektor Fitur dan \textit{State} Sebelumnya: Sel menerima vektor fitur $x_t$, \textit{hidden state} $h_{t-1}$, dan \textit{cell state} $C_{t-1}$.

\noindent b.~~Inisialisasi \textit{State} Awal: Pada langkah waktu pertama, $h_0$ dan $C_0$ diinisialisasi sebagai vektor nol berdimensi 24 sesuai jumlah \textit{hidden units}.

\noindent c.~~Penggabungan Vektor Masukan: Vektor $h_{t-1}$ dan $x_t$ digabungkan menjadi satu vektor yang digunakan bersama oleh seluruh gerbang.

\noindent d.~~Perhitungan \textit{Forget Gate}: Nilai $f_t$ dihitung dengan Persamaan~\ref{eq:gerbang-lupa} untuk menentukan proporsi informasi \textit{cell state} sebelumnya yang dipertahankan.

\noindent e.~~Perhitungan \textit{Input Gate}: Nilai $i_t$ dihitung dengan Persamaan~\ref{eq:gerbang-masukan} untuk menentukan besar informasi baru yang masuk ke \textit{cell state}.

\noindent f.~~Perhitungan Kandidat \textit{Cell State}: Kandidat $\tilde{C}_t$ dihitung dengan Persamaan~\ref{eq:kandidat-sel} menggunakan fungsi aktivasi tanh.

\noindent g.~~Pembaruan \textit{Cell State}: \textit{Cell state} diperbarui dengan Persamaan~\ref{eq:pembaruan-sel}, yaitu penjumlahan $f_t \odot C_{t-1}$ dan $i_t \odot \tilde{C}_t$.

\noindent h.~~Perhitungan \textit{Output Gate}: Nilai $o_t$ dihitung dengan Persamaan~\ref{eq:gerbang-keluaran} untuk menentukan bagian \textit{cell state} yang dikeluarkan.

\noindent i.~~Perhitungan \textit{Hidden State}: \textit{Hidden state} $h_t$ dihitung dengan Persamaan~\ref{eq:keadaan-tersembunyi} melalui perkalian elemen $o_t$ dan $\tanh(C_t)$.

\noindent j.~~Pemeriksaan Langkah Waktu: Apabila masih terdapat langkah waktu tersisa, nilai $h_t$ dan $C_t$ diteruskan ke langkah berikutnya dan proses kembali ke tahap penggabungan.

\noindent k.~~Pengambilan \textit{Hidden State} Akhir: Setelah seluruh langkah waktu selesai, \textit{hidden state} terakhir $h_T$ diambil sebagai representasi ringkas \textit{sequence} masukan.

\noindent l.~~Regularisasi \textit{Dropout}: Nilai $h_T$ dilewatkan melalui \textit{dropout layer} berlaju 0,1 untuk mencegah ketergantungan berlebih antar-node.

\noindent m.~~Pemrosesan \textit{Dense Layer}: Hasil \textit{dropout} diproses \textit{dense layer} 16 neuron beraktivasi ReLU untuk mempelajari kombinasi non-linear representasi \textit{sequence}.

\noindent n.~~Penghasilan Prediksi \textit{Log-Return}: \textit{Output layer} satu neuron beraktivasi linear menghasilkan prediksi $\hat{r}_t$, yang selanjutnya direkonstruksi ke skala nominal Rupiah.

\textit{Flowchart} ini menunjukkan bahwa sel LSTM bekerja melalui tiga gerbang dalam mengatur aliran informasi antar-langkah waktu, sehingga model mampu mempelajari pola autokorelasi jangka pendek pada deret waktu penjualan harian.
\subsection{Perhitungan Metrik Evaluasi Pengujian}

Proses evaluasi menghasilkan nilai kesalahan prediksi untuk setiap data uji berdasarkan perbandingan antara nilai aktual $Y_t$ dan nilai prediksi $\hat{Y}_t$ pada skala nominal Rupiah. Penelitian ini menggunakan empat metrik evaluasi, yaitu \textit{Mean Absolute Error} (MAE), \textit{Root Mean Squared Error} (RMSE), \textit{symmetric Mean Absolute Percentage Error} (sMAPE), dan \textit{Mean Absolute Scaled Error} (MASE), yang landasan teorinya telah dijabarkan pada Subbab~2.2.8. Perhitungan keempat metrik tersebut dirumuskan sebagai berikut.

\begin{equation}
    \text{MAE} = \frac{1}{N}\sum_{t=1}^{N}\left|Y_t - \hat{Y}_t\right|
\end{equation}

\begin{equation}
    \text{RMSE} = \sqrt{\frac{1}{N}\sum_{t=1}^{N}\left(Y_t - \hat{Y}_t\right)^2}
\end{equation}

\begin{equation}
    \text{sMAPE} = \frac{100\%}{N}\sum_{t=1}^{N}\frac{\left|Y_t - \hat{Y}_t\right|}{\left(\left|Y_t\right| + \left|\hat{Y}_t\right|\right)/2}
\end{equation}

\begin{equation}
    \text{MASE} = \frac{\dfrac{1}{N}\sum_{t=1}^{N}\left|Y_t - \hat{Y}_t\right|}{\dfrac{1}{N-1}\sum_{t=2}^{N}\left|Y_t - Y_{t-1}\right|}
\end{equation}

\noindent Keterangan:

\begin{enumerate}
    \item $Y_t$ merupakan nilai penjualan aktual pada hari aktif ke-$t$.
    \item $\hat{Y}_t$ merupakan nilai penjualan hasil prediksi model pada hari aktif ke-$t$.
    \item $N$ merupakan jumlah seluruh data pengujian.
    \item Penyebut pada persamaan MASE merupakan MAE dari \textit{baseline Naive}, yaitu prediksi yang menyamakan nilai hari ini dengan nilai hari aktif sebelumnya.
\end{enumerate}

Nilai MAE dan RMSE dinyatakan dalam satuan Rupiah dan menunjukkan besaran kesalahan absolut prediksi, dengan RMSE memberikan penalti lebih besar terhadap kesalahan berskala ekstrem. Nilai sMAPE dinyatakan dalam persen sehingga memudahkan interpretasi kesalahan secara relatif. Sebagai konvensi implementasi metrik sMAPE, apabila penyebut bernilai nol (nilai aktual dan prediksi sama-sama nol), penyebut diganti dengan nilai 1 agar tidak terjadi galat pembagian dengan nol (\textit{division by zero}). Konvensi inilah yang diverifikasi pada pengujian \textit{white box}.

Nilai MASE digunakan sebagai metrik utama penentuan kelayakan model karena bersifat bebas skala dan membandingkan kinerja model secara langsung terhadap \textit{baseline Naive}. Model dinyatakan layak apabila nilai MASE model lebih kecil daripada MASE \textit{baseline Naive} pada data uji yang sama, yang berarti kesalahan prediksi model lebih kecil daripada kesalahan metode pembanding sederhana tersebut.

\subsection{Perancangan Pengujian \textit{White Box}}

Pengujian \textit{white box} bertujuan memverifikasi kebenaran logika internal dan jalur eksekusi kode pada fungsi kritis layanan API prediksi. Pengujian dilakukan dengan menelusuri jalur logika secara manual menggunakan masukan yang keluarannya telah dihitung lebih dahulu sebagai acuan kebenaran. Tiga fungsi yang diuji adalah sebagai berikut.
\begin{enumerate}
    \item Fungsi perhitungan \textit{Seasonal-Naive} (\textit{by\_dow}), untuk memverifikasi jalur percabangan logika ketika jumlah data historis per hari kerja mencukupi ($\geq k$), tidak mencukupi ($<k$), maupun tidak tersedia sama sekali (\textit{fallback}).
    \item Fungsi metrik evaluasi sMAPE dan MASE, untuk memverifikasi jalur penanganan kasus pembagian dengan nilai penyebut nol atau mendekati nol agar tidak menghasilkan galat pembagian (\textit{division by zero}).
    \item Fungsi prediksi rekursif (\textit{forecast\_hybrid\_stable}), untuk memverifikasi jalur eksekusi tiga mekanisme pengaman secara berurutan, yaitu \textit{clipping} \textit{log-return}, \textit{damping factor}, dan \textit{safety rail} nominal omzet.
\end{enumerate}

\subsection{Indikator Keberhasilan Penelitian}

Keberhasilan penelitian diukur melalui tiga indikator berikut, yang pencapaiannya dijawab pada Bab IV dan Bab V.
\begin{enumerate}
    \item Aplikasi \textit{Point of Sale} berfungsi mengelola transaksi penjualan, katalog produk, dan pelaporan penjualan, yang divalidasi melalui pengujian \textit{black box}.
    \item Model \textit{Long Short-Term Memory} terimplementasi pada sistem dan kinerjanya terukur secara objektif menggunakan metrik MAE, RMSE, sMAPE, dan MASE terhadap \textit{baseline}.
    \item Sistem menyajikan hasil prediksi dan laporan penjualan dalam bentuk visualisasi yang mudah dipahami pengguna.
\end{enumerate}

\subsection{Implementasi Layanan Prediksi (API)}

Modul kecerdasan buatan untuk kalkulasi prediksi penjualan harian dikembangkan menggunakan Python dan terdiri atas dua bagian yang saling melengkapi. Bagian pertama adalah \textit{pipeline} riset berbasis Jupyter Notebook yang melatih model prediksi LSTM (TensorFlow/Keras) pada tiga granularitas waktu (harian, mingguan, dan bulanan) beserta eksperimen augmentasi data sintetis TimeGAN (PyTorch). Bagian kedua adalah layanan API produksi berbasis \textit{framework} Flask yang di-\textit{deploy} pada platform Hugging Face dan diintegrasikan langsung dengan aplikasi POS, sehingga beban komputasi prediksi terpisah dari beban kerja transaksional kasir.

Layanan API produksi menyediakan tujuh \textit{endpoint} REST dengan fungsi sebagai berikut:
\begin{enumerate}
    \item \textbf{Endpoint Prediksi Penjualan} (\textit{/api/predict/daily}, \textit{/api/predict/weekly}, \textit{/api/predict/monthly}): Meramalkan omzet ke depan dengan tanggal prediksi yang otomatis melewati hari tutup (akhir pekan serta libur semester Januari/Juli). Berdasarkan hasil evaluasi komparatif pada penelitian ini (Subbab 4.4), metode penyaji yang dipilih pada \textit{endpoint} produksi adalah metode statistik paling stabil, yaitu \textit{Seasonal-Naive} ($k=4$, rata-rata empat kemunculan terakhir hari yang sama, kompromi antara responsivitas terhadap tren terbaru dan peredaman fluktuasi acak, setara dengan rentang sekitar satu bulan hari sejenis) untuk harian, \textit{Mean-4} untuk mingguan, dan \textit{Mean-3} untuk bulanan, dengan prediksi \textit{Naive} disertakan sebagai pembanding, sedangkan model LSTM hasil pelatihan didokumentasikan sebagai artefak riset (\textit{.keras}).
    \item \textbf{Endpoint Rekomendasi Operasional} (\textit{/api/recommendations/stock} dan \textit{/api/recommendations/target}): Menghasilkan rekomendasi alokasi anggaran belanja per kategori produk dan kuantitas stok produk teratas berdasarkan proyeksi omzet (dilengkapi \textit{safety buffer} 15\% dan peringatan khusus produk mudah basi), serta tiga tingkatan target omzet harian (konservatif, moderat, dan agresif) berbasis statistik 15 hari aktif terakhir.
    \item \textbf{Endpoint Pencatatan dan Status} (\textit{/api/sales/record} dan \textit{/api/status}): Menerima rekap penjualan harian dari aplikasi POS dan memperbaruinya ke dataset historis (\textit{upsert} per tanggal) agar dasar prediksi selalu mengikuti data terkini, serta memeriksa kesehatan layanan dan ketersediaan berkas data.
\end{enumerate}

Aplikasi Flutter memanggil \textit{endpoint} tersebut secara langsung melalui HTTPS dengan \textit{payload} agregat penjualan tanpa informasi identitas pelanggan, kemudian menyimpan hasil analisis sebagai \textit{snapshot} pada tabel \textit{smart\_analytics\_snapshots} di Supabase.

Inti implementasi \textit{endpoint} prediksi harian pada berkas \textit{app.py} disajikan pada Kode Program~\ref{lst:flask_daily} (dipersingkat). Metode \textit{Seasonal-Naive} dihitung dengan merata-ratakan $k$ kemunculan terakhir dari setiap hari kerja yang sama, dan tanggal prediksi dihasilkan dengan melewati hari tutup.

\begin{lstlisting}[caption={Implementasi Endpoint Prediksi Harian Seasonal-Naive (\textit{app.py})}, label={lst:flask_daily}]
@app.route('/api/predict/daily', methods=['GET', 'POST'])
def predict_daily():
    data = request.get_json(silent=True) or {}
    n_days = int(data.get("n_days", 7))
    k = int(data.get("k", 4))
    dfa = get_daily_dataframe(data.get("history", None))
    last_date = dfa['date'].max()

    # Seasonal-Naive: rata-rata k kemunculan terakhir
    # dari hari kerja yang sama (0=Senin ... 4=Jumat)
    by_dow = {}
    for dow in range(5):
        dow_data = dfa[dfa['day_of_week'] == dow]['revenue']
        if len(dow_data) >= k:
            by_dow[dow] = dow_data.tail(k).mean()
        elif len(dow_data) > 0:
            by_dow[dow] = dow_data.mean()
        else:
            by_dow[dow] = dfa['revenue'].tail(10).mean()

    # Naive: prediksi = omzet hari kerja terakhir
    naive_value = float(dfa['revenue'].iloc[-1])

    # Tanggal prediksi otomatis melewati hari tutup
    future_dates = generate_future_business_days(last_date, n_days)
    predictions = []
    for dt in future_dates:
        pred_sn = int(round(by_dow.get(dt.weekday(), naive_value)))
        predictions.append({
            "date": dt.strftime('%Y-%m-%d'),
            "predicted_revenue_seasonal_naive": pred_sn,
            "predicted_revenue_naive": int(round(naive_value))})
    return jsonify({"predictions": predictions}), 200
\end{lstlisting}

\subsection{Penyaringan Hari Aktif dan Transformasi Target Log-Return}

Pemodelan prediksi pada penelitian ini difokuskan pada granularitas harian dengan strategi prediksi satu langkah ke depan (\textit{one-step-ahead prediction}). Untuk mengatasi variansi data yang ekstrem akibat fluktuasi harian yang sangat tajam, target prediksi tidak diprediksi menggunakan bentuk nilai nominal mentah, melainkan menggunakan bentuk \textit{log-return} (selisih logaritmik) pendapatan antar hari aktif yang berurutan. Pendekatan residual ini dirancang agar model cukup mempelajari koreksi atau deviasi nilai pendapatan dari hari aktif sebelumnya, sehingga model secara tidak langsung mewarisi sifat autokorelasi jangka pendek yang kuat pada deret waktu transaksi.

Variabel masukan (\textit{features}) terdiri atas nilai log-return pendapatan target dan enam fitur kalender yang dikodekan secara siklik (\textit{cyclical encoding} sinus-kosinus untuk nomor minggu dalam setahun, bulan, dan hari kerja aktif) serta variabel biner Ramadan. Variabel jumlah transaksi harian dan kuantitas produk terjual secara sengaja dikeluarkan dari variabel masukan model prediksi untuk menghindari kebocoran data (\textit{data leakage}), karena kedua nilai tersebut belum tersedia saat modul prediksi dijalankan untuk memprediksi hari berikutnya. Proses penskalaan data dilakukan menggunakan metode \textit{Min-Max Scaling} yang dipasang (\textit{fit}) hanya pada data latih untuk mencegah terjadinya kebocoran informasi dari data uji.

\subsection{Implementasi Arsitektur Model LSTM}

Arsitektur model prediksi yang diimplementasikan adalah LSTM satu lapis (\textit{single-layer LSTM}) dengan 24 \textit{hidden units}, diikuti oleh lapisan \textit{Dropout} dengan laju 0,1 untuk regularisasi, satu lapisan \textit{Dense} dengan 16 neuron beraktivasi \textit{Rectified Linear Unit} (ReLU), dan diakhiri oleh satu lapisan keluaran (\textit{output layer}) tunggal beraktivasi linear. Model ini dirancang secara minimalis dengan total parameter terlatih hanya sebanyak 3.585 parameter. Pemilihan model berkapasitas rendah ini didasarkan pada jumlah data latih yang sangat terbatas (212 sampel sequence), sehingga penggunaan model LSTM berkapasitas besar (\textit{stacked layers}) akan berisiko tinggi memicu kegagalan konvergensi pelatihan atau bias \textit{overfitting}. Proses optimasi menggunakan metode Adam dengan \textit{learning rate} awal sebesar $5 \times 10^{-4}$, fungsi kerugian (\textit{loss function}) MSE, serta didukung \textit{callbacks} \textit{EarlyStopping} dan \textit{ReduceLROnPlateau}. Konstruksi arsitektur model beserta konfigurasi pelatihannya disajikan pada Kode Program~\ref{lst:build_lstm}.

\begin{lstlisting}[caption={Konstruksi Arsitektur LSTM Tersederhanakan dan Konfigurasi Pelatihan}, label={lst:build_lstm}]
LOOK_BACK = 7   # jendela masukan: 7 hari aktif
HORIZON   = 1   # prediksi 1 langkah ke depan
UNITS     = 24
DROPOUT   = 0.1

def build_lstm():
    m = Sequential([
        LSTM(UNITS, input_shape=(LOOK_BACK, len(FEATURES))),
        Dropout(DROPOUT),
        Dense(16, activation='relu'),
        Dense(HORIZON)
    ], name='lstm_hybrid_residual')
    m.compile(optimizer=Adam(5e-4), loss='mse', metrics=['mae'])
    return m

cb = [EarlyStopping('val_loss', patience=20,
                    restore_best_weights=True),
      ReduceLROnPlateau('val_loss', factor=0.5,
                        patience=8, min_lr=1e-6)]

model = build_lstm()
hist  = model.fit(X_tr, y_tr, validation_data=(X_va, y_va),
                  epochs=200, batch_size=16, callbacks=cb)
\end{lstlisting}

\subsection{Implementasi Augmentasi Data Sintetis TimeGAN}

Sebagai upaya mitigasi terhadap keterbatasan ukuran dataset yang menjadi akar penyebab ketidakstabilan model LSTM, dilakukan eksperimen augmentasi data sintetis menggunakan \textbf{TimeGAN} (Yoon et al., 2019). Model TimeGAN yang diimplementasikan dengan PyTorch dilatih pada jendela deret waktu sepanjang 24 hari aktif dengan tiga fitur numerik (omzet, jumlah transaksi, dan kuantitas terjual) melalui tiga fase pelatihan (\textit{autoencoder}, \textit{supervised}, dan \textit{joint adversarial training}) masing-masing sebanyak 600 \textit{epoch}, kemudian menghasilkan 298 sekuens data harian sintetis dari 199 sekuens data riil (rasio augmentasi 1,5). Pada skenario ini, model LSTM multi-langkah (\textit{look-back} 14 hari aktif, horizon 7 hari) selanjutnya dilatih dalam dua kondisi: hanya menggunakan 199 sekuens data riil (\textit{baseline real-only}), dan menggunakan gabungan data riil dengan 298 sekuens sintetis (rasio augmentasi 1,5). Hasil evaluasi perbandingan kedua kondisi tersebut disajikan pada Subbab 4.4.3.

Cuplikan implementasi dua dari lima jaringan penyusun TimeGAN pada berkas \textit{TimeGAN.py}, yaitu jaringan \textit{embedder} yang memetakan data riil ke ruang laten dan \textit{generator} yang memetakan derau acak menjadi representasi laten sintetis, disajikan pada Kode Program~\ref{lst:timegan}.

\begin{lstlisting}[caption={Implementasi Jaringan \textit{Embedder} dan \textit{Generator} TimeGAN (PyTorch)}, label={lst:timegan}]
class EmbedderNet(nn.Module):
    """Memetakan data nyata X -> representasi laten H."""
    def __init__(self):
        super().__init__()
        self.rnn  = nn.GRU(NUM_FEAT, HIDDEN_DIM,
                           NUM_LAYERS, batch_first=True)
        self.proj = nn.Sequential(
            nn.Linear(HIDDEN_DIM, HIDDEN_DIM), nn.Sigmoid())

    def forward(self, x):
        h, _ = self.rnn(x)
        return self.proj(h)

class GeneratorNet(nn.Module):
    """Memetakan noise Z -> laten sintetis E."""
    def __init__(self):
        super().__init__()
        self.rnn  = nn.GRU(NUM_FEAT, HIDDEN_DIM,
                           NUM_LAYERS, batch_first=True)
        self.proj = nn.Sequential(
            nn.Linear(HIDDEN_DIM, HIDDEN_DIM), nn.Sigmoid())

    def forward(self, z):
        h, _ = self.rnn(z)
        return self.proj(h)

# 1) train_embedder : autoencoder embedder-recovery
# 2) train_supervisor: dinamika temporal ruang laten
# 3) train_joint    : pelatihan gabungan adversarial
\end{lstlisting}

\subsection{Implementasi Prediksi Rekursif Multi-Langkah}

Untuk kebutuhan penyajian visualisasi ramalan penjualan harian selama 7 hari aktif ke depan secara rekursif (\textit{recursive forecasting}), model LSTM residual yang melakukan iterasi mandiri mengalami kerentanan berupa penumpukan kesalahan (\textit{error propagation}) di mana nilai prediksi meluruh secara eksponensial hingga bernilai sangat kecil dan tidak realistis. Setelah ditambahkan mekanisme pengaman berupa \textit{clipping} pada \textit{log-return} (dijepit antara persentil 10--90 data latih), \textit{damping factor} ($\phi = 0.7$) untuk meredam perubahan pada horizon yang jauh, serta \textit{safety rail} penahan nominal omzet harian aktif, grafik prediksi yang dihasilkan menjadi lebih stabil dan realistis. Implementasi inti dari fungsi prediksi rekursif beserta ketiga mekanisme pengaman tersebut disajikan pada Kode Program~\ref{lst:recursive}.

\begin{lstlisting}[caption={Prediksi Rekursif dengan \textit{Clipping}, \textit{Damping}, dan \textit{Safety Rail}}, label={lst:recursive}]
# Batas clip dari persentil 10-90 log-return data latih
LR_LO, LR_HI = np.percentile(_train_logret, [10, 90])
REV_FLOOR = np.percentile(_act_rev, 2)   # rail bawah
REV_CEIL  = _act_rev.max()               # rail atas

def forecast_hybrid_stable(model, dfa, scaler, features,
                           look_back, n_steps, phi=0.7):
    window   = scaler.transform(
        dfa.tail(look_back)[features].values)
    prev_rev = float(dfa['revenue'].iloc[-1])
    d, step, rows = pd.Timestamp(dfa['date'].max()), 0, []
    while len(rows) < n_steps:
        d += pd.Timedelta(days=1)
        # Lewati hari tutup (akhir pekan, Januari & Juli)
        if d.weekday() >= 5 or d.month in [1, 7]:
            continue
        step += 1
        raw_lr  = float(inv_logret(
            model.predict(window[np.newaxis])[0, 0]))
        lr_clip = float(np.clip(raw_lr, LR_LO, LR_HI))  # 1) clip
        lr_damp = lr_clip * (phi ** (step - 1))         # 2) damp
        rev = float(np.expm1(np.log1p(prev_rev) + lr_damp))
        rev = float(np.clip(rev, REV_FLOOR, REV_CEIL))  # 3) rail
        # Susun baris fitur baru utk tanggal d (dipersingkat)
        raw = build_feature_row(d, raw_lr)
        # Geser jendela masukan dengan baris fitur baru
        window   = np.vstack([window[1:],
                              scaler.transform([raw])[0]])
        prev_rev = rev
        rows.append({'tanggal': d.date(),
                     'prediksi_revenue': int(round(rev))})
    return pd.DataFrame(rows)
\end{lstlisting}

Secara statistik, prediksi rekursif jangka panjang berbasis LSTM pada data terbatas ini akan dengan cepat meredam menuju nilai rata-rata historis (sifat \textit{mean-reverting}) dan menyerupai prediksi naif. Untuk diintegrasikan ke dalam fitur aplikasi riil kasir, metode prediksi statistik \textit{SARIMA} dan \textit{Seasonal-Naive} (rata-rata hari sejenis pada minggu sebelumnya) lebih direkomendasikan karena memberikan hasil prediksi multi-langkah yang jauh lebih stabil dan konsisten. Rekomendasi ini diwujudkan pada layanan API produksi, di mana \textit{endpoint} prediksi menyajikan metode \textit{Seasonal-Naive} ($k=4$) sebagai metode penyaji utama prediksi harian kepada aplikasi POS. Dalam penelitian skripsi ini, hasil evaluasi akurasi ilmiah tetap didasarkan pada pengujian satu langkah ke depan (\textit{one-step-ahead}), sedangkan visualisasi prediksi multi-langkah diposisikan murni sebagai ilustrasi fungsionalitas sistem.

\subsection{Implementasi Fungsi Metrik Evaluasi}
Sesuai rancangan pada Subbab~3.4.4, akurasi model diukur menggunakan empat metrik secara simultan, yaitu MAE, RMSE, sMAPE, dan MASE, dengan MASE sebagai acuan performa utama karena ternormalisasi terhadap galat naif \textit{in-sample}. MAPE konvensional tidak digunakan karena \textit{dataset} memuat hari aktif dengan pendapatan mendekati nol, yang menyebabkan galat persentase membesar tidak wajar (\textit{exploding MAPE}). Sebagai pembanding pada skema satu langkah ke depan digunakan \textit{Naive} (realisasi hari sebelumnya), \textit{Mean-7} (rata-rata tujuh hari aktif terakhir), \textit{Seasonal-Naive}, dan \textit{SARIMA} dengan skema \textit{rolling one-step}. Implementasi fungsi sMAPE dan MASE disajikan pada Kode Program~\ref{lst:metrics}.

\begin{lstlisting}[caption={Implementasi Fungsi Metrik Evaluasi sMAPE dan MASE}, label={lst:metrics}]
def smape(y, yhat):
    # sMAPE: galat dibagi rata-rata |aktual| dan |prediksi|
    d = (np.abs(y) + np.abs(yhat)) / 2
    return np.mean(np.abs(y - yhat)
                   / np.where(d == 0, 1, d)) * 100

def mase(y, yhat, naive_mae):
    # MASE: galat dinormalisasi thd galat naif in-sample
    return mean_absolute_error(y, yhat) / naive_mae

def report(y, yhat, naive_mae, label):
    rmse = np.sqrt(mean_squared_error(y, yhat))
    mae  = mean_absolute_error(y, yhat)
    return {'rmse': rmse, 'mae': mae,
            'smape': smape(y, yhat),
            'mase': mase(y, yhat, naive_mae)}
\end{lstlisting}

\section{Pembahasan Hasil Penelitian}

Bagian ini membahas temuan hasil implementasi, kontribusi fitur offline-first terhadap kelancaran operasional kasir, serta kemampuan analitik prediksi LSTM dalam meminimalkan masalah persediaan barang.

\subsection{Analisis Dominasi Persistensi Jangka Pendek pada Data Kantin Institusional}
Dalam konteks operasional kantin kampus EatsTEDI UGM, dominasi komponen persistensi ini sangat nyata karena nilai pendapatan harian sangat berkorelasi kuat dengan nilai pendapatan hari aktif sebelumnya. Pola ketergantungan jangka pendek ini ditangkap dengan sangat presisi oleh model \textit{Naive} (kemarin) yang memiliki kesalahan MAE terendah sebesar Rp 519.841,00.

\subsection{Analisis Kegagalan LSTM Mengungguli Baseline: Over-Smoothing pada Data Pendek}
Secara keseluruhan, hasil pengujian menunjukkan bahwa pada dataset transaksi penjualan kantin EatsTEDI UGM dengan 313 hari aktif, model LSTM, termasuk varian hybrid residual yang merupakan konfigurasi terbaik, tidak mengungguli metode pembanding sederhana (\textit{Naive} dan \textit{Mean-7}) maupun model statistik \textit{SARIMA} secara rata-rata, dan hanya mampu kompetitif pada kasus terbaiknya (1 dari 10 percobaan \textit{multi-seed}). Hasil evaluasi ini bukan merupakan suatu kegagalan atau anomali sistem, melainkan sejalan dengan temuan luas dalam berbagai literatur prediksi deret waktu komersial ritel (seperti pada kompetisi prediksi global M3 dan M4). Literatur tersebut membuktikan bahwa metode statistik klasik dan naif kerap mengungguli pendekatan pembelajaran mendalam (\textit{deep learning}) ketika data historis yang tersedia relatif terbatas dan deret waktu didominasi secara kuat oleh komponen persistensi jangka pendek.

Di sisi lain, model LSTM Hybrid yang memiliki kapasitas parameter lebih besar cenderung melakukan penghalusan nilai prediksi secara berlebihan (\textit{over-smoothing}) pada data latih yang pendek, sehingga tidak mampu menangkap lonjakan-lonjakan ekstrem omzet harian yang dipicu oleh dinamika aktivitas mahasiswa di lapangan.

\subsection{Analisis Ketidakstabilan Model akibat Keterbatasan Volume Data}
Pengujian multi-seed pada Skenario~2 memperlihatkan bahwa ketidakunggulan LSTM tidak hanya bersifat rata-rata, tetapi juga disertai ketidakstabilan yang tinggi. Nilai MAE dari sepuluh kali pelatihan tersebar pada rentang Rp495.527 sampai Rp1.048.967 dengan simpangan baku Rp145.024, sehingga galat percobaan terburuk lebih dari dua kali lipat galat percobaan terbaik. Sebaran yang lebar ini merupakan gejala khas pelatihan jaringan saraf pada data berukuran kecil, yaitu proses optimasi sangat peka terhadap inisialisasi bobot acak karena jumlah sekuens latih tidak cukup untuk menuntun model menuju solusi yang konsisten. Implikasinya, pelaporan performa berdasarkan satu kali pelatihan saja berpotensi menyesatkan, baik karena kebetulan memperoleh hasil terbaik maupun terburuk. Hal inilah yang mendasari penggunaan sebaran nilai, bukan nilai tunggal, sebagai dasar penarikan kesimpulan pada penelitian ini.

\subsection{Analisis Kontribusi dan Batas Efektivitas Augmentasi TimeGAN}
Sebagai upaya mengatasi akar permasalahan keterbatasan data tersebut, penelitian ini turut menguji peran augmentasi data sintetis menggunakan TimeGAN. Hasil eksperimen menunjukkan bahwa penambahan sekuens sintetis mampu memperbaiki kualitas pembelajaran model LSTM secara substansial (penurunan MAE sekitar 50,8\% dibandingkan model tanpa augmentasi pada skema multi-langkah), yang menandakan bahwa kegagalan LSTM pada penelitian ini memang bersumber dari kelangkaan data, bukan dari kesalahan arsitektur semata. Namun demikian, model LSTM teraugmentasi tetap belum melampaui \textit{baseline} \textit{Seasonal-Naive}, sehingga augmentasi sintetis diposisikan sebagai pelengkap yang menjanjikan, bukan pengganti, dari akumulasi data transaksi riil jangka panjang.

\subsection{Analisis Interpretasi Nilai MASE Lebih dari Satu}
Seluruh metode yang diuji pada Skenario~1 menghasilkan nilai MASE lebih besar dari satu, berkisar antara 1,432 untuk \textit{Naive} sampai 1,840 untuk LSTM Hybrid. Secara harfiah, nilai tersebut berarti galat seluruh metode pada data uji lebih besar daripada galat prediksi naif \textit{in-sample} yang menjadi penyebutnya. Kondisi ini tidak menandakan kesalahan perhitungan, melainkan mencerminkan bahwa periode data uji memiliki fluktuasi pendapatan harian yang lebih tinggi dibandingkan periode data latih, sehingga acuan normalisasi yang dihitung dari data latih menjadi relatif rendah. Oleh karena itu, MASE pada penelitian ini lebih tepat dibaca sebagai ukuran pembanding relatif antarmetode daripada sebagai ambang kelayakan absolut. Dibaca dengan cara tersebut, urutan MASE tetap konsisten dengan urutan MAE dan RMSE, yaitu \textit{Naive} paling baik dan LSTM Hybrid paling lemah, sehingga kesimpulan perbandingan antarmetode tidak berubah.

\subsection{Analisis Keputusan Metode Penyaji pada Layanan Produksi}
Hasil keempat skenario menghasilkan rekomendasi praktis bagi pengelola: pada volume data UMKM saat ini, metode statistik sederhana lebih layak diintegrasikan sebagai penyaji dasbor prediksi harian, sedangkan LSTM baru relevan ditinjau kembali apabila data historis telah bertambah signifikan (minimal 3--5 tahun operasional). Rekomendasi tersebut telah diterapkan pada penelitian ini, yaitu layanan API produksi menyajikan \textit{Seasonal-Naive} ($k=4$) untuk prediksi harian, \textit{Mean-4} untuk mingguan, dan \textit{Mean-3} untuk bulanan, sementara model LSTM dan hasil augmentasi TimeGAN didokumentasikan sebagai artefak riset. Perlu dicatat secara terbuka bahwa hasil pengujian pada Tabel~\ref{tab:eval_baseline_comp} menunjukkan \textit{Seasonal-Naive} ($k=4$) belum merupakan pilihan optimal untuk prediksi satu hari ke depan, karena metode \textit{Naive} mencatat galat yang lebih rendah. Pemilihan \textit{Seasonal-Naive} pada layanan produksi didasari pertimbangan keterbacaan pola mingguan bagi pengguna, sehingga penyesuaian metode penyaji menjadi \textit{Naive} merupakan perbaikan yang dapat dilakukan secara langsung tanpa mengubah arsitektur layanan yang bersifat \textit{model-agnostic}.

Keputusan tersebut memisahkan dua hal yang berbeda namun saling terkait, yaitu metode yang dievaluasi sebagai objek kajian penelitian dan metode yang benar-benar disajikan layanan produksi. Karena arsitektur layanan bersifat \textit{model-agnostic}, model LSTM dapat langsung diaktifkan sebagai penyaji begitu data mencukupi untuk mengungguli \textit{baseline}, tanpa mengubah aplikasi \textit{mobile}. Adapun granularitas mingguan dan bulanan pada Subbab~4.1.3 merupakan fitur pelengkap visualisasi \textit{Smart Analytics} dan berada di luar lingkup evaluasi bab ini, yang berfokus pada granularitas harian sesuai Batasan Masalah.

\subsection{Pembahasan Kelayakan Fungsional dan Kontribusi Arsitektur Offline-First}
Hasil pengujian \textit{black box} pada 12 skenario menunjukkan tingkat kesuksesan 100\% ("Berhasil"). Integrasi antara basis data lokal Isar DB dan basis data cloud Supabase terbukti sangat andal. Melalui skema sinkronisasi yang dirancang, kasir tidak perlu bergantung pada koneksi internet saat menginput transaksi. Hal ini menghilangkan risiko terhambatnya antrean kasir akibat koneksi internet yang lambat atau terputus secara tiba-tiba.

Penggunaan local database Isar DB juga memberikan performa loading data yang sangat cepat. Secara observasi, operasi baca-tulis produk dan transaksi lokal terasa hampir seketika (\textit{near-instant}) dan jauh lebih responsif dibandingkan operasi yang bergantung pada pemanggilan REST API database cloud secara langsung, yang turut dipengaruhi oleh kondisi dan latensi jaringan. Hal ini meningkatkan efisiensi kerja kasir secara signifikan. Perlu dicatat bahwa perbandingan ini bersifat observasi kualitatif, bukan hasil pengukuran latensi terstruktur (mis. jumlah sampel, alat ukur, dan kondisi jaringan yang terkendali), sehingga angka waktu tempuh kuantitatif belum dapat dilaporkan pada penelitian ini.

\subsection{Posisi Temuan terhadap Penelitian Terdahulu}
Sebagian besar penelitian terdahulu yang ditinjau pada Subbab~2.1 melaporkan keunggulan LSTM atau variannya dibandingkan metode pembanding. Perbedaan hasil dengan penelitian ini tidak terletak pada implementasi arsitektur, melainkan pada karakteristik data yang dimodelkan. Penelitian-penelitian tersebut umumnya menggunakan deret waktu dengan cakupan historis bertahun-tahun serta pola musiman yang telah berulang beberapa siklus penuh, sehingga jaringan saraf memperoleh cukup contoh untuk mempelajari struktur temporal yang berulang. Sebaliknya, data penelitian ini hanya mencakup 313 hari aktif, belum genap dua siklus tahun akademik, dan didominasi komponen persistensi jangka pendek yang justru paling efisien ditangkap oleh metode naif.

Dengan demikian, temuan bahwa LSTM belum mengungguli \textit{baseline} pada penelitian ini tidak bertentangan dengan literatur, melainkan melengkapinya dengan menandai batas bawah volume data yang diperlukan agar pendekatan pembelajaran mendalam memberikan nilai tambah pada konteks UMKM. Kontribusi tersebut ditopang oleh ketelitian metodologis evaluasi yang diterapkan, yaitu:
\begin{enumerate}
    \item \textbf{Penggunaan Model Pembanding (\textit{Baselines}) yang Tepat:} Menyandingkan model LSTM dengan metode naif, rata-rata bergerak, dan SARIMA untuk memvalidasi apakah penambahan kompleksitas komputasi model AI memberikan nilai tambah akurasi prediksi yang sepadan.
    \item \textbf{Pemilihan Metrik Evaluasi yang Valid:} Menggunakan sMAPE dan MASE yang tahan terhadap pembagian bernilai nol atau sangat kecil pada hari-hari libur, menghindari kesalahan \textit{exploding MAPE} yang menyesatkan.
    \item \textbf{Pengujian Kestabilan melalui Multi-Seed:} Melaporkan sebaran nilai performa model dari sepuluh kali pelatihan secara acak, sehingga mengungkap ketidakstabilan model LSTM pada ukuran data yang kecil secara transparan.
    \item \textbf{Eksplorasi Augmentasi Data Sintetis:} Menguji efektivitas TimeGAN sebagai strategi mitigasi keterbatasan data pada prediksi penjualan UMKM, lengkap dengan kuantifikasi perbaikan galat terhadap model tanpa augmentasi dan posisinya relatif terhadap \textit{baseline} musiman.
\end{enumerate}

\section{Keterbatasan Sistem dan Penelitian}

Meskipun sistem POS mobile dengan fitur prediksi penjualan harian ini telah berhasil diimplementasikan dan diuji, terdapat beberapa keterbatasan operasional maupun metodologi penelitian yang harus diperhatikan.

\subsection{Keterbatasan Sistem POS}

Beberapa keterbatasan operasional dari sistem POS mobile yang dikembangkan meliputi:
\begin{enumerate}
    \item \textbf{Keterbatasan Cold Start pada Toko Baru}:
    Model prediksi LSTM memerlukan data transaksi historis runtun waktu yang kontinu. Sebagaimana dijelaskan pada Subbab~3.4, model secara teknis membutuhkan minimal 7 hari aktif transaksi (panjang \textit{sequence} \texttt{LOOK\_BACK}) agar dapat dijalankan sama sekali, namun hasil proyeksi baru dianggap cukup andal untuk ditampilkan tanpa peringatan \textit{cold start} setelah data transaksi terkumpul minimal selama 30 hari sebagai periode pemanasan awal (\textit{warm-up period}).
    
    \item \textbf{Ketergantungan Data Terkini}:
    Meskipun operasional transaksi kasir dapat berjalan tanpa internet (offline), kualitas proyeksi modul prediksi LSTM bergantung pada kelengkapan data transaksi aktual yang menjadi \textit{payload} permintaan analisis. Jika data transaksi terbaru belum tercatat atau tersinkronkan, akurasi hasil proyeksi prediksi untuk hari berikutnya dapat menurun karena tidak menangkap tren transaksi paling akhir.
    
    \item \textbf{Ketergantungan Akses Server untuk Hasil Prediksi}:
    Karena keterbatasan sumber daya komputasi dan konsumsi baterai perangkat mobile, proses kalkulasi prediksi model LSTM yang berat dialihkan sepenuhnya ke layanan inferensi Python yang di-\textit{hosting} pada platform Hugging Face. Akibatnya, meskipun kasir dapat bertransaksi secara offline, pengguna tetap memerlukan koneksi internet aktif untuk memperbarui visualisasi prediksi analitik terbaru dari API inferensi ke dasbor aplikasi. Selain itu, layanan inferensi gratis pada Hugging Face dapat mengalami kondisi \textit{cold start} (jeda pemuatan saat \textit{server} baru aktif kembali dari \textit{idle}) yang memperlambat respons analisis pertama.
\end{enumerate}

\subsection{Keterbatasan Penelitian Model Prediksi}

Keterbatasan utama dalam pemodelan prediksi pada penelitian ini meliputi:
\begin{enumerate}
    \item \textbf{Keterbatasan Volume Dataset}: Jumlah data transaksi aktif riil dari platform EatsTEDI UGM relatif sedikit untuk standar pemodelan pembelajaran mendalam (\textit{deep learning}), yakni hanya 313 hari aktif yang menyusut menjadi sekitar 212 sampel latih setelah pembentukan sequence. Keterbatasan ini berdampak langsung pada tingginya sensitivitas model terhadap inisialisasi bobot acak awal (\textit{seed variance}) yang memicu ketidakstabilan akurasi model.
    
    \item \textbf{Keterbatasan Pengamatan Pola Musiman Jangka Panjang}: Rentang waktu transaksi yang kurang dari dua tahun belum memungkinkan model LSTM untuk mempelajari pola musiman tahunan (\textit{annual seasonality}) secara utuh dan komprehensif.
    
    \item \textbf{Deret Waktu yang Terputus-putus}: Banyaknya hari non-aktif transaksi akibat libur kalender akademik kampus (seperti sepanjang bulan Januari dan Juli) serta akhir pekan menyebabkan deret waktu menjadi patah dan terputus-putus, yang menyulitkan jaringan saraf dalam mempelajari dependensi keterkaitan temporal jangka panjang secara kontinu.

    \item \textbf{Bias Penyaringan Hari Aktif (\texttt{revenue > 0})}: Penyaringan data pada tahap \textit{preprocessing} hanya mempertahankan hari kerja yang memiliki pendapatan positif (\texttt{revenue > 0}), sebagaimana dijelaskan pada Subbab~3.1. Konsekuensinya, hari kerja aktif dengan penjualan nol yang sebenarnya nyata turut terbuang dari dataset, bukan hanya akhir pekan atau libur kalender akademik. Akibat lanjutannya, deret \textit{log-return} $r_t$ yang menjadi target model dihitung antar hari aktif berurutan yang jarak kalender riilnya tidak seragam -- dapat berupa 1 hari, namun juga dapat mencapai lebih dari 10 hari setelah masa libur panjang. Ketidakseragaman interval waktu ini melanggar sebagian asumsi keteraturan deret waktu (\textit{regular time-series}) yang mendasari arsitektur LSTM, dan diduga turut menjadi salah satu faktor yang memperberat kesulitan model dalam mempelajari pola dependensi temporal secara konsisten.
\end{enumerate}

\chapter[PENUTUP]{\\ PENUTUP}

Bab ini menyajikan kesimpulan penelitian yang disusun mengikuti tujuan penelitian pada Subbab~1.3, serta saran bagi pengembangan penelitian selanjutnya.

\section{Kesimpulan}

Berdasarkan hasil perancangan, implementasi, dan pengujian yang telah dilakukan, diperoleh kesimpulan sebagai berikut.
\begin{enumerate}
    \item Aplikasi \textit{Point of Sale} berbasis \textit{mobile} dengan fitur prediksi penjualan harian berhasil dibangun menggunakan \textit{framework} Flutter, basis data lokal Isar DB, layanan \textit{cloud} Supabase, serta layanan prediksi berbasis Flask yang di-\textit{deploy} pada Hugging Face. Fitur prediksi terintegrasi ke dalam alur kerja transaksi melalui halaman \textit{Smart Analytics}, sehingga hasil peramalan dapat langsung diakses pengelola tanpa keluar dari aplikasi. Arsitektur \textit{offline-first} memungkinkan kasir tetap bertransaksi tanpa koneksi internet, dengan sinkronisasi otomatis ketika koneksi kembali aktif. Pengujian \textit{black box} terhadap 12 kasus penggunaan utama berhasil seluruhnya, pengujian \textit{white box} terhadap tiga fungsi kritis pada layanan prediksi sesuai dengan hasil perhitungan manual, dan pengujian mekanisme sinkronisasi membuktikan tidak terjadi kehilangan maupun duplikasi data transaksi.

    \item Model \textit{Long Short-Term Memory} dengan pendekatan \textit{hybrid residual} berhasil diterapkan pada \textit{dataset} EatsTEDI yang berjumlah 313 hari aktif. Evaluasi \textit{multi-seed} menghasilkan MAE sebesar Rp667.718,00 $\pm$ Rp145.024,00, RMSE sebesar Rp897.563,00 $\pm$ Rp165.804,00, sMAPE sebesar 38,06\% $\pm$ 3,96\%, dan MASE sebesar 1,840 $\pm$ 0,400, dengan sebaran MAE yang lebar (Rp495.527,00--Rp1.048.967,00) sehingga model belum stabil pada ukuran data tersebut. Augmentasi data sintetis TimeGAN menurunkan MAE model pada skema multi-langkah dari Rp1.750.355,00 menjadi Rp860.695,00, yaitu perbaikan sekitar 50,8\%. Temuan ini menunjukkan bahwa keterbatasan performa model bersumber dari kelangkaan data, bukan dari kesalahan arsitektur, namun augmentasi sintetis berperan sebagai pelengkap dan belum dapat menggantikan akumulasi data transaksi riil.

    \item Pada skema satu langkah ke depan, model LSTM (MASE 1,840) belum mengungguli \textit{baseline} \textit{Naive} yang mencatat galat terkecil dengan MAE Rp519.841,00 dan MASE 1,432, maupun \textit{SARIMA} dan \textit{Mean-7}. Pada pengujian horizon prakiraan $h = 1$ sampai $h = 7$ hari aktif, mekanisme \textit{clipping}, peredaman $\varphi = 0{,}7$, dan \textit{safety rail} berhasil menjaga galat model tetap stabil pada MASE 2,124--2,505 tanpa degradasi seiring bertambahnya horizon, tetapi \textit{baseline} \textit{Seasonal-Naive} tetap lebih akurat pada seluruh horizon (MASE 2,012--2,140). Dengan demikian, pada volume data setara penelitian ini pendekatan \textit{deep learning} belum memberikan nilai tambah akurasi yang sepadan dengan kompleksitasnya, sehingga metode statistik sederhana lebih layak digunakan sebagai penyaji prediksi. Penerapan LSTM baru relevan ditinjau kembali apabila data historis telah mencakup sekitar tiga sampai lima tahun operasional, dan hal tersebut dapat dilakukan tanpa mengubah aplikasi karena arsitektur layanan prediksi bersifat \textit{model-agnostic}.
\end{enumerate}

\section{Saran}

Beberapa saran yang dapat diajukan untuk pengembangan penelitian selanjutnya adalah sebagai berikut.
\begin{enumerate}
    \item Penelitian lanjutan disarankan menggunakan rentang data yang lebih panjang, yaitu sekitar tiga sampai lima tahun operasional, agar model dapat mempelajari pola musiman tahunan secara berulang dan hipotesis keunggulan \textit{deep learning} dapat diuji pada kondisi data yang memadai.

    \item Variabel masukan model dapat ditambah dengan fitur \texttt{gap\_days}, yaitu jarak hari kalender terhadap hari aktif sebelumnya, untuk mengurangi dampak ketidakseragaman interval waktu akibat penyaringan hari aktif sebagaimana dibahas pada Subbab~4.7.2.

    \item Permasalahan \textit{cold start} pada toko baru dapat diatasi menggunakan \textit{transfer learning} atau pelatihan model \textit{global} dari data toko sejenis, sehingga prediksi dapat disajikan sebelum riwayat transaksi toko mencukupi.

    \item Pendekatan pemodelan dapat dikembangkan menjadi model \textit{hybrid}, misalnya ARIMA-LSTM atau LSTM-GRU, guna menggabungkan kemampuan model statistik dalam menangkap komponen musiman dengan kemampuan jaringan saraf dalam menangkap pola non-linear.

    \item Keamanan data transaksi yang tersimpan pada perangkat dapat ditingkatkan dengan mengaktifkan enkripsi basis data lokal Isar DB menggunakan kunci yang dikelola secara aman oleh perangkat.

    \item Fungsionalitas aplikasi dapat diperluas dengan integrasi gerbang pembayaran untuk menghasilkan kode QRIS dinamis, serta notifikasi multi-kanal seperti WhatsApp API untuk menyampaikan ringkasan omzet harian dan peringatan stok menipis kepada pemilik toko.
\end{enumerate}
